# 属性建模规范

## 1. 文档目的

本文档用于固定当前系统中“属性”这一模型的正式规范，作为后续以下模块的共同基础：

- 新增页与编辑页中的属性选择、属性渲染与属性录入
- “我的”页面中的属性管理
- 属性模板与属性定义之间的关系建模
- 规则模型与属性模型之间的边界划分
- 后续数据库结构、表单生成与规则绑定实现

本文档重点回答以下问题：

- 属性定义到底由哪些部分组成
- 值类型、值属性、值来源、交互方式如何分层
- 价格、百分比、带单位数值这类场景应该落在哪一层
- 属性值如何承接物品上的实际结果
- 什么内容属于属性本身，什么内容不属于属性本身

---

## 2. 核心共识

当前阶段固定以下共识：

1. 物品是主体。
2. 属性是服务于物品的字段。
3. 一个属性只能有一个主值定义。
4. 简单属性本质上就是一个可配置的键值对字段。
5. 属性模型负责“字段是什么、怎么配置、怎么交互”。
6. 复杂的跨属性计算不属于属性本身，而属于规则模型。
7. 模板不是主模型本体，而是帮助用户创建属性或规则的母板。

也就是说：

- 属性模型负责“字段是什么、值长什么样、从哪来、怎么填”
- 规则模型负责“多个字段怎么一起算”

---

## 3. 属性模型的范围

当前阶段，属性模型只包含两个核心对象：

1. 属性定义
2. 属性值

当前不把以下对象纳入属性模型本体：

- 复杂规则
- 跨字段关联关系
- 周期执行逻辑
- 通用公式引擎

这些内容统一交给规则模型承担。

---

## 4. 物品与属性的关系

物品是最终承载数据的实体，可以理解为一条记录。

一个物品由以下两类信息共同描述：

- 系统内置字段
- 一组属性值

因此当前可固定为：

- 一个物品可以拥有多个属性值
- 一个属性定义可以被多个物品复用

---

## 5. 属性定义

## 5.1 属性定义是什么

属性定义回答的是：

- 这个属性叫什么
- 这个属性值本质上是什么类型
- 这个属性有哪些类型专属配置
- 这个属性的值从哪里来
- 这个属性在 UI 上如何交互
- 这个属性默认绑定了哪些规则

属性定义是用户在“属性管理”中真正创建和维护的对象。

## 5.2 属性定义的核心字段

当前建议属性定义严格收敛为以下 6 项：

1. 属性名
2. 值类型
3. 值属性
4. 值来源
5. 交互方式
6. 规则绑定

### 5.2.1 属性名

属性名用于表达这个字段在业务上的基础语义。

例如：

- 购入价格
- 定金
- 购买日期
- 品牌
- 状态

在最简单的使用方式下，属性名本身就承载了字段语义。

### 5.2.2 值类型

值类型回答的是：

- 这个属性值本质上是什么数据形态

当前建议第一阶段稳定支持以下 5 类：

1. 文本
2. 数值
3. 日期
4. 布尔
5. 选择

说明：

- 这层只负责值形态，不直接承载复杂计算逻辑
- `选择` 是一个独立值类型，统一承接单选、多选、下拉、多标签选择等场景
- 文本、数值、日期、布尔四类不再在值类型层承担单选、多选语义

### 5.2.3 值属性

值属性回答的是：

- 当前值类型之下，还需要哪些专属配置，才能完整表达这个字段

它的作用是让属性既保留统一主模型，又能表达足够靠近用户端的业务语义。

不同值类型建议支持的值属性如下：

- 文本
  - 文本类型仅占位，无必须配置
  - 可选配置可包括：是否多行、占位提示、最大长度

- 数值
  - 可配置：数值格式、单位、百分比、小数位数、默认值、是否允许负数
  - 数值格式建议至少支持：
    - 普通数值
    - 价格
    - 百分比
    - 带单位数值

- 日期
  - 可配置：日期格式、是否包含时间、默认值

- 布尔
  - 可配置：真值文案、假值文案、默认值

- 选择
  - 可配置：选项列表、是否多选、选项池来源、是否允许用户在使用时新增选项、默认值

其中需要特别固定一条：

- `价格` 不是一个独立值类型
- `价格` 是 `数值` 类型下的一种数值格式

也就是说：

- `购入价格`
  - 值类型：数值
  - 值属性：数值格式 = 价格，单位类型 = 币种，默认单位 = CNY

### 5.2.4 值来源

值来源回答的是：

- 这个属性的值最终来自哪里

当前建议固定为三大类：

1. `输入`
2. `固定值`
3. `来自系统`

其中：

- `输入`
  - 表示用户直接填写或选择

- `固定值`
  - 表示值来自固定值池或固定选项池
  - 如果值类型为 `选择`，这里可继续细分：
    - 系统选项池
    - 用户选项池
    - 混合选项池

- `来自系统`
  - 表示值来自 App 的系统级变量，而不是当前物品表单中的用户直接输入
  - 例如：
    - 账户创建时间
    - 已加入 App 时长
    - 当前日期
    - 当前时间
    - 当前日历时间
    - 当前定位
    - 全局总价值
    - 某个规则写入后的系统衍生变量

这里需要特别统一：

- 属性里的 `来自系统`
- 规则输入里的 `系统来源`
- 规则输出里的 `写入系统`

三者说的都是同一类东西，即 App 内部的系统级来源与系统级承接目标，而不是某个具体物品自己的补充属性。

进一步说：

- `系统级变量`
  - 更偏运行期全局变量
  - 例如账户创建时间、当前日期、当前时间、当前定位、全局总价值

- `系统设置`
  - 不再作为与系统级变量平级的数据来源
  - 它更适合作为系统级变量的配置承接层
  - 例如：
    - 全局总价值的基准币种
    - 统一日历时间的时区
    - 当前定位的定位精度

因此：

- 如果一个属性的值来源配置为 `来自系统`
  - 本质上就是读取某个系统级变量
- 属性模型需要进一步声明它绑定的是哪个系统级变量
- 如果一个规则的输入来源配置为 `系统来源`
  - 本质上也是读取某个系统级变量
- 如果一个规则的输出目标配置为系统变量
  - 本质上就是把规则结果写入 App 的系统级变量槽位

### 5.2.5 交互方式

交互方式回答的是：

- 当前属性在 UI 上通过什么控件和什么方式让用户完成录入或确认

固定原则如下：

- 交互方式是可配置的
- 但不是完全自由的一层
- 用户只能在“当前值类型 + 当前值来源 + 当前值属性”支持的交互方式集合中选择

例如：

- 文本 + 输入
  - 单行输入框
  - 多行输入框
  - 标签输入

- 数值 + 输入
  - 数字输入框
  - 价格输入框
  - 百分比输入框
  - 带单位数值输入框

- 日期 + 输入
  - 日期选择器
  - 日期时间选择器
  - 文本格式输入

- 布尔 + 输入
  - 开关
  - 单选“是/否”
  - 文本“对/错”

- 选择 + 固定值
  - 单选
  - 多选
  - 下拉选择
  - 标签选择

需要特别强调：

- 布尔类型不必只绑定开关
- 数值类型也不必只绑定普通数字框
- 交互方式应作为用户可配置的一层，但必须受上层约束

### 5.2.6 规则绑定

规则绑定回答的是：

- 当前这个属性默认绑定了哪些规则
- 这些规则中，当前属性扮演什么输入角色
- 这些规则还依赖哪些其他属性

固定规则如下：

- 一个属性允许绑定多个规则
- 属性定义只声明“我绑定了哪些规则”
- 规则本体的计算逻辑仍然属于规则模型

例如：

- `购入价格`
  - 可绑定：
    - `计入总价`
    - `平均价值`

- `定金`
  - 可绑定：
    - `待付尾款`

## 5.3 属性定义的边界

属性定义负责：

- 定义字段名称
- 定义值类型
- 定义值属性
- 定义值来源
- 定义交互方式
- 定义默认规则绑定关系

属性定义不负责：

- 执行平均价值计算
- 执行待付尾款计算
- 执行周期扣费逻辑
- 承担规则本体的计算步骤

这些都属于规则模型。

---

## 6. 属性值

## 6.1 属性值是什么

属性值回答的是：

- 某个物品在这个属性上的实际填写结果

例如：

- 属性定义：`品牌`
- 属性值：`Sony`

- 属性定义：`购买日期`
- 属性值：`2026-06-01`

- 属性定义：`标签`
- 属性值：`["耳机", "降噪"]`

- 属性定义：`购入价格`
- 属性值：`{ amount: 599.0, currency: "CNY" }`

## 6.2 属性值的边界

属性值只承载结果，不承载规则。

也就是说：

- 属性值不负责计算平均价值
- 属性值不负责计算待付尾款
- 属性值不负责计算周期扣费

这些都属于规则层。

## 6.3 属性值允许是结构化结果

虽然一个属性只有一个主值定义，但属性值不要求永远是单个原始标量。

在值属性有明确约束的情况下，属性值可以承接结构化结果。

例如：

- 价格型数值
  - 主值仍然是数值
  - 但其属性值可包含：
    - 金额
    - 币种

- 带单位数值
  - 主值仍然是数值
  - 但其属性值可包含：
    - 数值
    - 单位

这里的结构化结果仍然属于“同一个主值定义”的展开，不意味着属性重新膨胀成多主值对象。

---

## 7. 属性模型的最高约束

## 7.1 一个属性只有一个主值定义

这是当前模型的最高约束。

固定规则如下：

- 一个属性只能有一个主值
- 主值决定该属性最核心的值形态与交互形态
- 不能把多个并列主值塞回同一个属性，导致属性重新膨胀成业务对象

例如：

- `品牌` 的主值是文本
- `购买日期` 的主值是日期
- `购入价格` 的主值是数值
- `状态` 的主值是选择

## 7.2 简单属性优先是轻量字段

按当前规范，最简单的属性定义本质上就是：

- 一个有名字的字段
- 一个值类型
- 一个值来源方式
- 一个交互方式

如果进入更复杂的使用方式，则属性定义还可以声明：

- 该属性有哪些值属性配置
- 该属性绑定了哪些规则
- 这些规则是否会引入额外依赖属性

这使得属性系统首先是轻量可用的，而不是一开始就变成复杂建模器。

---

## 8. 属性与规则的边界

## 8.1 属性负责承载数据

属性模型负责：

- 字段定义
- 字段值
- 值来源方式
- 值属性配置
- 交互方式
- 默认规则绑定关系

## 8.2 规则负责跨属性计算

规则模型负责：

- 多个属性之间的计算
- 属性与时间之间的计算
- 周期性逻辑
- 衍生结果的推导

例如：

- 平均价值
- 待付尾款
- 周期扣费
- 订阅已支付

需要单独固定一条：

- 价格的币种、百分比格式、带单位数值的单位定义，属于属性定义中的值属性
- 不属于规则模型
- 规则只消费这些属性值，不负责定义这些值的格式

## 8.3 当前不单独建立关系模型

当前阶段不单独建立第三套“关系模型”。

原因是：

- 属性之间的关联，本质上可以先隐含在规则的输入绑定中
- 如果单独抽出关系模型，系统会迅速变重
- 当前更重要的是让“简单属性可用、复杂规则可配”

---

## 9. 属性与模板的关系

模板不是主模型，而是创建母板。

在当前阶段，应固定以下关系：

- 模板负责提供标准起点
- 属性定义是模板的具体化结果
- 属性值是具体定义在物品上的实际填写结果

可以表达为：

`属性模板 -> 属性定义 -> 属性值`

## 9.1 用户创建属性优先从模板出发

当前不推荐用户面对一片空白直接搭建字段模型。

更推荐的方式是：

1. 先选择属性模板
2. 再修改属性名
3. 再确认值类型、值属性、值来源、交互方式
4. 最后决定是否启用模板允许范围内的规则绑定

## 9.2 空白创建本质上也是从基础模板创建

即使用户选择“从零创建属性”，系统内部也不应是真正空白。

更准确的实现应是：

- 文本属性 -> 基础文本模板
- 数值属性 -> 基础数值模板
- 日期属性 -> 基础日期模板
- 选择型属性 -> 基础选择模板

也就是说，“从零创建”只是产品表达上的简化，不是系统建模上的无模板。

---

## 10. 物品表单中的属性添加逻辑

当用户为某个物品添加一个属性时，系统不应只添加当前属性本身，还应检查该属性绑定的规则。

推荐流程如下：

1. 用户选择一个属性
2. 系统将该属性加入当前物品的填写清单
3. 系统检查该属性绑定的规则
4. 对每条规则，读取其必需依赖属性
5. 若依赖属性尚未出现在当前物品填写清单中，则自动补齐
6. 若依赖属性已存在，则直接复用，不重复添加

固定边界如下：

- 自动补齐的对象是规则依赖输入，不是规则输出
- 只自动补必需依赖属性，不强行补可选依赖属性
- 已存在的依赖属性不重复添加
- 规则输出优先以只读结果形式呈现

---

## 11. 第一阶段固定边界

当前阶段固定以下边界，避免过度设计：

### 11.1 当前正式支持

- 属性定义
- 属性值
- 属性模板
- 模板允许范围内的规则绑定配置

### 11.2 当前不开放

- 用户自定义任意公式
- 用户创建任意新规则类型
- 用户发明任意新属性结构
- 把属性系统做成通用低代码平台

### 11.3 当前重点

当前阶段更重要的是：

- 让属性管理稳定
- 让属性定义足够轻
- 让规则与属性边界清晰
- 让后续模板与规则模板回写有清晰锚点

---

## 12. 最终固定方案

当前可以固定的属性建模方案如下：

1. 一个物品可以看作一条记录，一个属性可以看作这条记录上的一个字段。
2. 当前属性模型只包含：属性定义、属性值。
3. 属性定义当前先严格收敛为：
   - 属性名
   - 值类型
   - 值属性
   - 值来源
   - 交互方式
   - 规则绑定
4. 一个属性只能有一个主值定义。
5. 属性值只承载结果，不承载跨字段计算。
6. 属性之间的复杂关联与计算，统一交给规则模型承担。
7. 当前不单独建立关系模型，关系先隐含在规则绑定中。
8. 模板不是主模型，而是创建母板，后续应明确分为属性模板与规则模板。
