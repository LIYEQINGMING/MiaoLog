# 分类体系设计方案

## 1. 文档目的

本文档用于固定“物品分类体系”的设计方向，作为后续以下模块的统一依据：

- 新增页中的分类选择交互
- 后续“我的”页面中的分类管理页
- 搜索与筛选中的分类维度
- 模板与分类的绑定关系
- 数据层从“分类 + 子分类”向“多层级分类树”迁移的设计基础

本文档当前聚焦的是方案设计，不直接展开具体代码实现。

---

## 2. 为什么要调整分类设计

当前系统仍然保留了以下旧思路：

- `分类`
- `子分类`

这种二段式结构只适用于非常浅的分类体系，一旦后续需要支持更细的组织方式，就会遇到明显问题：

1. 只能自然支持两级，不适合扩展到三级、四级或更多层级。
2. 新增页中需要分别处理 `分类` 和 `子分类`，交互会越来越重。
3. 后续分类管理页如果继续沿用这一思路，会很难维护。
4. 搜索、筛选、模板绑定都不容易与“树状分类”对齐。

因此，分类系统应从“分类 + 子分类”升级为“多层级分类树”。

---

## 3. 设计目标

分类体系应满足以下目标：

1. 支持多层级分类，而不是固定两级。
2. 新增页只保留一个 `分类` 入口，不再单独暴露 `子分类` 字段。
3. 后续分类管理页可以对整棵分类树进行管理。
4. 允许分类逐步演进，而不影响新增页主流程。
5. 能兼容当前阶段的代码现状，并为后续 `categoryId` 化预留迁移空间。

---

## 4. 核心定义

为了统一后续讨论，这里先固定几个概念。

### 4.1 分类节点

分类树中的任意一个节点，称为“分类节点”。

例如：

- `电子产品`
- `音频设备`
- `头戴耳机`

### 4.2 分类路径

从根节点到当前节点的一整条路径，称为“分类路径”。

例如：

- `电子产品`
- `电子产品 / 音频设备`
- `电子产品 / 音频设备 / 头戴耳机`

### 4.3 分类树

所有分类节点及其父子关系构成的层级结构，称为“分类树”。

---

## 5. 新分类体系的核心结论

### 5.1 用户看到的字段仍然叫“分类”

新增页中，基础信息区仍然保留一个字段：

- `分类`

但这个字段背后不再只是“一级分类名称”，而是承载“分类路径选择”的统一入口。

### 5.2 新增页中去掉“子分类”

基础信息区不再单独展示：

- `子分类`

用户不再先选分类、再选子分类，而是通过点击 `分类` 进入分类选择器，一次完成完整路径的选择。

### 5.3 支持多层级，但 UI 先按 3 层优化

从领域模型上，分类体系应支持多层级。

从第一阶段 UI 体验上，可以先重点优化常见的 1~3 层场景：

- 一级分类
- 二级分类
- 三级分类

这样既不把系统锁死在两级，也不会让第一版交互过重。

### 5.4 父分类允许直接作为最终分类

不是所有物品都必须落到最末级分类。

例如：

- 用户可以直接选择 `电子产品`
- 也可以进一步选择 `电子产品 / 音频设备`
- 还可以继续选择 `电子产品 / 音频设备 / 头戴耳机`

也就是说：

`父分类允许直接挂物品。`

这个规则非常重要，它能显著降低分类体系的使用门槛。

## 6. 新增页中的分类交互设计

### 6.1 基础信息区结构调整

基础信息区固定为：

1. `名称`
2. `分类`
3. `数量`

`子分类` 从基础信息区中移除。

### 6.2 分类行的展示方式

新增页中的 `分类` 这一行，应展示：

- 当前分类图标
- 当前分类名称

例如：

- `💻 电子产品`
- `🎧 音频设备`
- `🎧 头戴耳机`

如果未选择分类，则显示：

- 图标占位
- `选择分类`

点击分类行后，分类选择器展示完整路径。

这里固定一条展示规则：

- 基础信息区默认只展示“当前选中的分类名称 + 图标”
- 完整分类路径放在分类选择器内部展示

这样可以保证新增页保持简洁，不让完整路径长期占用表单空间。

### 6.3 分类选择器的职责

点击 `分类` 后，进入统一的“分类选择器”。

分类选择器负责：

- 浏览分类树
- 搜索分类
- 逐级进入子节点
- 选择当前节点作为最终分类「通过点击确认按钮」
- 在当前层级新建分类

### 6.4 分类选择器推荐交互

建议分类选择器包含以下区域：

1. 搜索框 / 路径展示器
2. 当前路径面包屑
3. 当前层级分类列表
4. 新建当前层级分类入口
5. 底部确认动作

### 6.5 分类列表的展示形式

分类列表建议采用：
- 顶部路径面包屑展示「类似于文件夹的路径框，正好可以把检索也放在这里」
- 当前层级下的分类列表「类似于文件夹列表」

如果某个分类节点没有子级，也仍然可以直接选中。

如果某个分类节点有子级，用户可以：

- 继续进入下一级“文件夹”
- 或直接将当前节点作为最终分类

这里再固定一条交互规则：

- 点击某个分类节点时，默认行为是“进入该节点”
- 当前节点是否作为最终分类，由底部确认按钮决定
- 即使当前节点没有子级，也建议保持同一套确认逻辑，避免有的节点点击即选中、有的节点点击即进入，导致交互混乱

### 6.6 搜索行为

分类选择器中的搜索应支持：

- 搜索已有分类节点
- 直接匹配路径中的任意层级名称
- 搜索不到时允许新建分类，但是需要提示用户确认是否新建分类

例如搜索：

- `耳机`
- `音频`
- `冬装`

都应该能定位到相关分类节点或分类路径。

### 6.7 新建分类行为

在分类选择器内，用户应可新建分类。

新建时需要明确当前上下文：

- 在当前层级下新建子分类
- 通过搜索框输入完整路径新建分类「需要包含新分类名称」

例如：

- 在当前层级新建 `收藏`
- 在当前层级 `衣物` 下新建 `鞋类`
- 在搜索框输入 `衣物 / 鞋类 / 跑鞋` 后新建 `跑鞋`

## 7. 分类管理页的职责设计

后续“我的”页面应增加 `分类管理` 页面，用于统一管理分类树。

### 7.1 分类管理页的核心职责

分类管理页应承担以下职责：

- 查看整棵分类树
- 新增一级分类
- 在任意节点下新增子分类
- 编辑分类
- 调整排序
- 删除分类
- 搜索分类节点
- 查看某分类下物品数量
- 合并分类

### 7.2 第一版推荐优先级

分类管理页第一版建议优先支持：

1. 查看分类树
2. 新增分类
3. 新增子分类
4. 编辑名称和logo
5. 查看分类下物品数量
6. 删除分类

以下能力可作为第二阶段：

- 拖拽调整层级
- 合并分类
- 批量迁移物品
- 批量排序

### 7.3 推荐页面结构

分类管理页推荐包含两个主要视图：

- `树状管理视图`
- `搜索 / 列表「文件夹」视图`

优先做：

- `搜索 / 列表「文件夹」视图`

---

## 8. 需要提前固定的分类规则

为了避免后续设计和开发反复返工，建议现在先固定以下规则。

### 8.1 层级深度规则

建议支持多层级，不在数据模型层面限制死为二级或三级。

UI体验通过「文件夹」式的路径展示和选择，提升使用体验。

### 8.2 同名规则

建议规则如下：

- 不允许同一父级下出现重名分类
- 允许不同父级下存在同名分类

例如：

- `电子产品 / 配件`
- `相机 / 配件`

这两种情况应允许存在。

### 8.3 父分类挂载规则

建议允许父分类直接挂物品。

即：

- 不强制要求用户必须选到叶子节点

### 8.4 删除规则

建议将删除规则明确分成以下几类：

- 无子分类、无物品引用的分类：允许直接删除
- 无子分类、但已被物品引用的分类：允许删除，但必须二次确认，并明确告知影响范围
- 有子分类的分类：不允许直接删除，必须先迁移、合并或清空其子节点关系

删除后，如有物品失去原分类引用，建议统一归入：

- `未分类`

而不是保留为空值，避免后续筛选、统计和编辑中出现脏数据。

### 8.5 重命名规则

建议允许重命名分类。

重命名后，应自动影响所有引用该分类的物品展示结果。

## 9. 数据建模建议

### 9.1 长期目标：categoryId 化

长期来看，更合理的做法是：

- 物品不再直接存储“分类字符串”
- 物品只存储 `categoryId`
- 展示分类路径时，通过分类表回推出完整路径

### 9.2 推荐分类表结构

后续分类体系建议设计为独立分类表，例如：

- `id`
- `name`
- `parentId`
- `sortOrder`
- `icon`
- `isEnabled`
- `createdAt`
- `updatedAt`

必要时还可以增加：

- `pathCache`
- `level`

用于优化展示和搜索。

### 9.3 物品侧建议存储

长期建议：

- `categoryId`

必要时可额外缓存：

- `categoryPathSnapshot`

用于降低复杂查询成本或保留历史展示语义。

## 10. 与当前代码现状的兼容策略

考虑到当前系统中仍然大量使用：

- `分类`
- `子分类`
- 字符串型字段

因此建议采用分阶段迁移，而不是一次性完全替换。

### 10.1 第一阶段：UI 收口

第一阶段先完成以下动作：

- 新增页移除 `子分类` 独立字段
- 新增页保留单一 `分类` 入口
- `分类` 改为进入统一分类选择器

这一阶段主要解决交互收口问题。

### 10.2 第二阶段：路径字符串过渡

在数据层还未完全 `categoryId` 化之前，可暂时采用：

- `分类` 字段存完整路径字符串

例如：

- `电子产品 / 音频设备 / 头戴耳机`

这是一种过渡方案，优点是：

- 兼容当前代码结构
- 不需要立刻做大规模数据库迁移
- 可先把新增页和分类管理的交互跑通

### 10.3 第三阶段：正式 categoryId 化

等分类管理页和分类树数据表稳定后，再进行正式迁移：

- 新增分类表
- 物品改为引用 `categoryId`
- 将历史 `分类 / 子分类` 字符串数据迁移到分类节点关系中

## 11. 与模板系统的关系

分类体系后续还需要与模板系统协同。

### 11.1 模板绑定建议

模板绑定：

- 分类节点

这样就可以实现任意层级分类都可以有模板。

这里再固定一条规则：

- 模板可绑定任意层级的分类节点
- 绑定后，新增页默认定位到该分类节点
- 用户仍然可以在该节点基础上继续下钻到更细的分类

这样可以避免模板与分类体系绑定过死，同时保留多层级选择的灵活性。

### 11.2 模板驱动效果

当用户选择模板后：

- 可自动填充默认分类路径
- 可限制推荐的分类范围
- 可根据分类自动挂载补充属性

例如：

- `耳机模板` 默认推荐 `电子产品 / 音频设备 / 耳机`
- `鞋类模板` 默认推荐 `衣物 / 鞋类`

---

## 12. 与搜索和筛选的关系

分类树确定后，搜索和筛选也应统一基于分类路径或分类节点进行。

### 12.1 搜索建议

搜索时可支持：

- 按节点名搜索
- 按路径搜索
- 按父分类聚合搜索

### 12.2 筛选建议

筛选时建议支持：

- 仅筛某个具体分类节点
- 同时包含其全部子分类

例如筛选：

- `电子产品`

可选择是否同时包含：

- `电子产品 / 音频设备`
- `电子产品 / 音频设备 / 头戴耳机`
- `电子产品 / 相机`

---

## 13. 推荐的设计结论

当前可固定的分类方向如下：

1. 分类体系升级为多层级分类树。
2. 新增页基础信息区只保留 `名称 / 分类 / 数量`。
3. `子分类` 从新增页中移除，不再作为独立字段出现。
4. `分类` 统一通过分类选择器进行选择。
5. 分类选择器支持浏览、搜索、逐级进入、当前层级新建分类。
6. 父分类允许直接作为最终分类。
7. 后续“我的”页面增加独立的 `分类管理` 页面。
8. 数据层采用分阶段迁移：先 UI 收口，再路径字符串过渡，最终 `categoryId` 化。

---

## 14. 后续建议讨论点

在正式进入开发前，建议再进一步明确以下几个问题：

1. 分类选择器第一版做成 `全屏页面` 还是 `底部弹层`
2. 分类管理页第一版是否支持 `拖拽调整层级`
3. 分类删除时的迁移流程如何设计
4. 模板绑定分类时是否允许绑定父分类
5. 搜索筛选里是否默认包含子分类

这些问题确认后，就可以继续输出下一份更具体的设计文档，例如：

- 分类选择器交互稿
- 分类管理页信息架构方案
- 分类数据结构与迁移方案
