# 价格属性设计文档

## 1. 文档目的

本文档用于固定当前系统中“价格属性”的统一设计方案，作为后续：

- 新增页与修改页 UI 设计
- 高级自定义属性能力设计
- 模板系统设计
- 统计与计算规则设计
- 数据结构演进

的统一依据。

本文档重点解决的问题是：

- 价格相关属性很多，但语义容易混乱
- 价格值、价格动作、周期规则不能继续散落在不同区块中
- 系统内置价格属性与用户自定义价格属性，需要共用同一套模型

---

## 2. 核心前提

### 2.1 产品语义前提

当前系统是“个人物品/资产管理”系统，不是库存管理系统。

因此，这里讨论的“价格属性”是：

- 物品的价格相关属性
- 物品的价格相关补充信息
- 价格参与系统统计与计算的规则

而不是：

- 进销存价格体系
- 库存成本核算体系
- 财务软件级别的记账模型

### 2.2 页面结构前提

新增页和修改页当前采用：

- 基础信息区
- 补充信息区

两区结构。

因此，价格相关内容不再单独占用页面级“功能区”，而是统一收口到：

- `补充信息区中的价格属性块`

---

## 3. 设计目标

价格属性设计需要同时满足以下目标：

1. 让系统内置价格属性和用户自定义价格属性使用同一套结构。
2. 让价格值、动作配置、周期规则保持在同一个属性块中。
3. 避免“购入价格”“总价”“定金”“订阅价格”等字段散乱堆叠。
4. 避免页面级功能控制项和属性本体脱节。
5. 为未来扩展更多价格角色与价格动作预留空间。
6. 当前阶段保持产品能力可控，不开放无限制自定义动作系统。

---

## 4. 问题抽象

当前价格相关信息之所以容易混乱，是因为它们实际上混合了三种不同层次的内容：

1. `价格事实`
2. `价格计算规则`
3. `价格周期规则`

例如：

- `购入价格`
- `总价`
- `定金`
- `订阅价格`

属于价格事实。

而：

- `是否计入总价`
- `是否参与均价计算`
- `是否参与日均价值计算`

属于价格计算规则。

而：

- `是否订阅制`
- `订阅周期`
- `自动续费`
- `下次扣费日`

属于价格周期规则。

如果继续把这三类内容拆散，就会导致：

- 用户不知道哪些开关是给哪个价格用的
- 页面结构越来越碎
- 内置属性和自定义属性难以统一

因此，价格设计必须改为“价格属性块”模型。

---

## 5. 统一模型

### 5.1 价格属性块

系统中的每一个价格相关属性，都应被视为一个完整的：

- `价格属性块`

一个价格属性块至少包含以下四部分：

1. 它是什么价格
2. 它的金额是多少
3. 它是否参与哪些计算
4. 它是否带周期规则

为了让信息完整，实际模型中还应补充第五项：

5. 它发生在什么时间

因此，一个价格属性块的完整表达建议是：

- 属性名
- 金额
- 币种
- 日期
- 计算动作配置
- 周期规则配置

### 5.2 统一适用范围

以下内容都应统一纳入价格属性块模型：

- 系统内置价格属性
- 模板带入的价格属性
- 用户自定义价格属性

例如：

- `购入价格`
- `总价`
- `定金`
- `尾款`
- `订阅价格`
- `会员费`
- `保养费用`

都应走同一套结构。

---

## 6. 两层结构

为了同时支持“属性可复用”和“每件物品的值不同”，价格属性应拆成两层：

### 6.1 价格属性定义层

定义层解决的是：

`这个价格属性是什么。`

它至少包含：

- 属性名
- 属性类型，固定为 `PRICE`
- 价格语义角色
- 支持哪些动作
- 是否支持周期规则
- 默认动作值

### 6.2 价格属性值层

值层解决的是：

`这件具体物品上的这个价格属性填了什么。`

它至少包含：

- 金额
- 币种
- 日期
- 是否参与总价
- 是否参与均价
- 是否参与日均价值
- 是否周期性
- 周期类型
- 自动续费
- 下次扣费日

### 6.3 为什么必须拆层

如果不拆层，后续会出现问题：

- 同一个价格属性定义无法在不同物品上复用
- 模板难以复用价格属性
- 用户创建一个价格属性后，系统无法区分“属性本身”和“这次填写的值”

因此，价格属性必须固定为：

- `定义层`
- `值层`

的双层模型。

---

## 7. 价格属性定义规范

### 7.1 必填项

用户或系统创建一个价格属性定义时，至少要明确：

- 它叫什么
- 它是什么类型，固定为 `PRICE`
- 它支持哪些动作
- 它是否允许周期配置

### 7.2 推荐字段

建议价格属性定义至少包含以下信息：

| 字段 | 含义 |
| :--- | :--- |
| `name` | 属性名称，如购入价格、定金、会员费 |
| `type` | 固定为 `PRICE` |
| `role` | 价格语义角色 |
| `supportedActions` | 当前支持的计算动作集合 |
| `supportsRecurrence` | 是否支持周期规则 |
| `defaultActions` | 默认动作开关值 |
| `defaultCurrency` | 默认币种，可选 |

### 7.3 价格语义角色

为了让内置价格属性和自定义价格属性更稳定，建议引入：

- `role`

角色字段。

推荐内置角色包括：

- `PURCHASE_UNIT_PRICE`：购入单价
- `PURCHASE_TOTAL_PRICE`：购入总价
- `DEPOSIT_PRICE`：定金
- `BALANCE_PRICE`：尾款
- `SUBSCRIPTION_PRICE`：订阅价格
- `CURRENT_VALUE_PRICE`：当前估值
- `CUSTOM_PRICE`：自定义价格

角色的意义是：

- 让系统可以给出更合理的默认动作
- 让统计与报表更容易收口
- 让 UI 能按角色给出更准确的说明

---

## 8. 价格属性值规范

### 8.1 价格值最小集合

每个价格属性值实例至少应包含：

- 金额
- 币种
- 日期

原因是：

- 没有金额就不是价格
- 没有币种就无法统一解释金额
- 没有时间，很多价格事实就不完整

### 8.2 推荐字段

建议价格属性值至少包含以下信息：

| 字段 | 含义 |
| :--- | :--- |
| `amount` | 金额 |
| `currency` | 币种 |
| `date` | 价格发生日期或记录日期 |
| `includeInTotal` | 是否参与总价统计 |
| `includeInAverage` | 是否参与均价计算 |
| `includeInDailyValue` | 是否参与日均价值计算 |
| `isRecurring` | 是否周期性价格 |
| `recurrenceType` | 周期类型 |
| `autoRenew` | 是否自动续费 |
| `nextChargeDate` | 下次扣费日 |

### 8.3 日期语义

价格属性值中的日期，不应一律解释成“购买日期”，而应解释为：

- 该价格事实发生的日期
- 或该价格记录的有效日期

例如：

- `购入价格` 对应购买日期
- `定金` 对应支付定金日期
- `尾款` 对应补款日期
- `订阅价格` 对应开始日期或生效日期

---

## 9. 价格动作配置

### 9.1 动作的定位

价格动作配置属于：

- 价格属性块内部配置

不再属于页面级功能区，不再作为散落的全局控制项出现。

### 9.2 当前建议开放的动作

当前阶段建议只开放少量稳定动作：

- `计入总价`
- `参与均价计算`
- `参与日均价值计算`

当前不建议开放：

- 用户自定义动作类型
- 用户自由定义复杂计算公式
- 不受约束的任意动作组合系统

### 9.3 文案建议

在 UI 上优先使用正向文案：

- `计入总价`
- `参与均价计算`
- `参与日均价值计算`

而不是优先使用负向文案：

- `不计入总价`
- `不参与均价`

原因是价格块本身已经信息较多，负向文案更容易导致理解错误。

### 9.4 默认规则建议

建议系统为不同价格角色提供默认动作值：

| 价格角色 | 计入总价 | 参与均价 | 参与日均价值 |
| :--- | :--- | :--- | :--- |
| 购入价格 | 开 | 开 | 开 |
| 总价 | 开 | 关 | 关 |
| 定金 | 关 | 关 | 关 |
| 尾款 | 关 | 关 | 关 |
| 订阅价格 | 关 | 关 | 关 |
| 当前估值 | 可配置 | 关 | 关 |

### 9.5 定义层驱动 UI

价格动作的展示能力，不应由前端页面自行猜测，而应由：

- `价格属性定义层`

直接驱动。

固定规则如下：

1. 定义层负责声明某个价格属性支持哪些动作。
2. 值层只保存当前已支持动作的具体值。
3. 前端只渲染定义层声明支持的动作。
4. 定义层未声明支持的动作，前端不展示对应 UI。

例如：

- 某个价格属性定义支持 `计入总价`
- 不支持 `参与均价计算`
- 支持周期规则

则前端应只展示：

- `计入总价`
- 周期配置区域

而不展示：

- `参与均价计算`

### 9.6 默认值初始化规则

当某个价格属性第一次被挂到物品上时，值层的动作配置应根据定义层默认值初始化。

也就是说：

- 定义层负责声明 `defaultActions`
- 值层首次创建时按 `defaultActions` 生成初始值
- 前端初次渲染时直接读取值层结果

例如：

- `购入价格` 默认：
  - `计入总价 = true`
  - `参与均价计算 = true`
- `定金` 默认：
  - `计入总价 = false`
  - `参与均价计算 = false`

这样可以保证：

- 系统内置价格属性有稳定默认行为
- 用户自定义价格属性也可以按定义层默认值自动初始化
- UI 不需要在前端额外硬编码一套默认逻辑

---

## 10. 周期规则配置

### 10.1 周期规则的定位

周期规则不再作为页面级“订阅专区”存在，而是作为：

- 某个价格属性块的附属配置

来出现。

### 10.2 哪些价格属性可以支持周期规则

不是所有价格属性都应该支持周期规则。

建议通过定义层中的：

- `supportsRecurrence`

来决定某个价格属性是否允许周期配置。

### 10.3 当前周期规则字段

如果某个价格属性支持周期规则，则可配置：

- 是否周期性
- 周期类型
- 自动续费
- 下次扣费日

周期类型当前建议支持：

- `DAY`
- `WEEK`
- `MONTH`
- `QUARTER`
- `YEAR`

### 10.4 订阅价格的最佳实践

`订阅制` 不建议继续作为一个全局散落字段存在。

更推荐的设计是：

- 把订阅价格视为一种特殊的价格属性块

也就是：

- 一次性价格块
- 周期性价格块

两种模式。

这样：

- `订阅价格`
- `自动续费`
- `扣费周期`
- `下次扣费日`

都可以自然地归属于同一个价格块。

## 11. 系统内置价格属性建议

当前建议将系统常见价格属性收敛为以下几类：

### 11.1 一次性价格属性

- `购入价格`
- `总价`
- `定金`
- `尾款`
- `当前估值`

### 11.2 周期性价格属性

- `订阅价格`
- `会员费`
- `租赁月费`
- `服务续费`

### 11.3 统一规则

以上内置价格属性全部都应使用同一套价格属性块 UI，只通过：

- 名称
- 默认动作
- 是否支持周期规则

来区分差异。

---

## 12. 用户自定义价格属性

### 12.1 用户可创建的内容

未来用户创建一种新的价格属性时，本质上只需要配置：

1. 它是什么价格
2. 它的金额是多少
3. 它是否参与哪些计算
4. 它是否带周期规则

在完整模型里，实际应进一步落实为：

- 属性名称
- 属性类型为 `PRICE`
- 是否支持统计动作配置
- 是否支持周期规则
- 默认动作值

### 12.2 推荐创建流程

用户创建一个自定义价格属性时，建议流程为：

1. 输入属性名称
2. 确认属性类型为 `PRICE`
3. 选择是否支持统计动作配置
4. 选择是否支持周期规则
5. 保存为新的价格属性定义

例如用户可以创建：

- `保养费用`
- `会员费`
- `租赁月费`
- `年费`

### 12.3 当前阶段的开放边界

当前阶段建议只开放：

- 创建价格属性
- 为价格属性配置系统已支持的动作
- 为价格属性配置系统已支持的周期规则

当前不开放：

- 用户自定义新的动作种类
- 用户自定义统计公式
- 用户自由创建任意复杂规则引擎

这样可以保证系统可控且易于实现。

## 13. UI 最佳实践

### 13.1 页面结构

页面层面保持不变：

- 基础信息区
- 补充信息区

价格相关属性全部放入：

- `补充信息区中的价格属性块`

### 13.2 价格属性块展示建议

一个典型价格属性块建议按以下顺序展示：

1. 属性名
2. 金额输入框
3. 币种选择
4. 日期
5. 计算动作配置
6. 周期规则配置

### 13.3 一次性价格块示例

```text
购入价格    [ 299.00 ] [ CNY ]
购买日期    [ 2026-05-18 ]
计入总价    [开]
参与均价    [开]
参与日均价值 [开]
```

### 13.4 定金价格块示例

```text
定金        [ 50.00 ] [ CNY ]
支付日期    [ 2026-05-01 ]
计入总价    [关]
参与均价    [关]
参与日均价值 [关]
```

### 13.5 周期性价格块示例

```text
订阅价格    [ 28.00 ] [ CNY ]
开始日期    [ 2026-05-18 ]
周期        [ 月 ]
自动续费    [开]
下次扣费日  [ 2026-06-18 ]
计入总价    [关]
参与均价    [关]
参与日均价值 [关]
```

### 13.6 展示原则

价格块的核心原则是：

- 属性值与属性动作不分离
- 周期规则与价格本体不分离
- 内置属性与自定义属性不分离

区别只在于：

- 名称不同
- 默认动作不同
- 是否支持周期规则不同

## 14. 数据结构建议

### 14.1 定义层建议

价格属性定义层建议至少有：

- `id`
- `name`
- `type = PRICE`
- `role`
- `supportedActions`
- `supportsRecurrence`
- `defaultActions`
- `defaultCurrency`

### 14.2 值层建议

价格属性值层建议至少有：

- `definitionId`
- `amount`
- `currency`
- `date`
- `includeInTotal`
- `includeInAverage`
- `includeInDailyValue`
- `isRecurring`
- `recurrenceType`
- `autoRenew`
- `nextChargeDate`

### 14.3 不支持与关闭的语义区分

在动作配置和值层设计中，必须严格区分：

- `不支持`
- `支持但关闭`

这两种不同语义。

推荐规则如下：

- `不支持`：使用 `null`、字段缺失，或不下发该字段
- `支持但关闭`：使用 `false`
- `支持且开启`：使用 `true`

这样做的原因是：

- 一个价格属性根本不支持某动作
- 和一个价格属性支持该动作但用户手动关闭

在语义上是两件完全不同的事，不能混为同一个 `false`。

### 14.4 设计原因

如果把“不支持”和“支持但关闭”都统一写成 `false`，后续会出现问题：

- 前端无法准确判断该不该显示某个动作
- 回填时无法准确知道这是能力缺失还是用户选择
- 统计层无法区分“字段不存在”和“字段被关闭”
- 数据迁移时容易误判旧值含义

因此，值层必须保留这种区分。

### 14.5 推荐表达方式

推荐按以下原则设计数据结构：

- 定义层通过 `supportedActions` 决定能力边界
- 值层只保存定义层允许出现的动作值
- 不支持的动作不应被强行写入值层

例如：

定义层：

- `supportedActions`
  - `includeInTotal = true`
  - `includeInAverage = false`
  - `includeInDailyValue = false`
  - `recurrence = true`

值层：

- `includeInTotal = true`
- `isRecurring = true`
- `recurrenceType = MONTH`

而：

- `includeInAverage`
- `includeInDailyValue`

由于定义层不支持，就不应在值层里作为一个普通 `false` 强行落下。

### 14.6 设计原则

数据结构层必须能表达：

- 一个价格属性定义可以被多个物品复用
- 一个物品可以拥有多个价格属性块
- 不同价格属性块可以拥有不同动作配置
- 周期规则只出现在支持周期的价格属性上
- 前端 UI 可以完全由定义层能力驱动
- 值层可以明确区分“未支持”和“支持但关闭”

## 15. 当前阶段建议落地范围

为了保证实现节奏，建议当前阶段先做最小可行落地：

### 15.1 第一阶段

先统一以下系统内置价格属性：

- `购入价格`
- `总价`
- `订阅价格`

并支持：

- 金额
- 币种
- 日期
- 计入总价
- 参与均价

### 15.2 第二阶段

补充支持：

- `定金`
- `尾款`
- `当前估值`
- 周期规则

### 15.3 第三阶段

再开放：

- 用户创建自定义价格属性
- 模板挂载价格属性定义

---

## 16. 最终固定方案

当前价格属性设计可固定为以下规则：

1. 价格相关内容统一采用“价格属性块”模型。
2. 每个价格属性块至少包含：属性名、金额、币种、日期、动作配置、周期规则。
3. 价格属性必须拆成“定义层”和“值层”。
4. 系统内置价格属性与用户自定义价格属性共用同一套结构。
5. 价格动作配置归属于价格属性块内部，不再独立成页面级功能区。
6. 周期规则归属于价格属性块内部，不再独立成页面级订阅区。
7. 前端 UI 只渲染定义层声明支持的动作与周期能力。
8. 值层仅保存定义层允许出现的动作值。
9. 不支持的动作与支持但关闭的动作必须严格区分，不能统一压成 `false`。
10. 当前阶段仅开放系统支持的动作与周期规则，不开放无限制自定义动作系统。

---

## 17. 设计原则总结

这一版价格属性设计的核心原则可以总结为：

1. 价格不是单一字段，而是一类属性块。
2. 价格事实、计算规则、周期规则必须分层，但在 UI 上要聚合展示。
3. 系统内置价格属性和用户自定义价格属性必须统一建模。
4. 属性值和属性动作不应分离到不同页面区块。
5. 周期性价格应被视为价格属性的一种模式，而不是独立专题。
6. 定义层决定前端能展示什么，值层只保存被允许的具体值。
7. `null` 与 `false` 必须保留不同语义，分别表示“不支持”和“支持但关闭”。
8. 当前阶段优先稳定模型与默认规则，不追求过早开放复杂自定义能力。
