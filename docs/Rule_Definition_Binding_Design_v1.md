# 规则定义与绑定设计稿 v1

## 1. 文档定位

本文档基于 `Attribute_Rule_Model_Draft.md` 中已经形成的顶层共识，进一步把“规则模型”细化为一份可直接指导产品设计、数据建模与代码实现的专项设计稿。

本文档重点回答以下问题：

- 规则定义在第一阶段到底要定义什么
- 规则绑定在第一阶段到底要绑定什么
- 用户从某个属性出发配置规则时，系统应该如何约束和引导
- 规则如何自然生成属性依赖关系
- 规则如何回接物品编辑页、属性删除影响分析与后续规则管理页

本文档不替代顶层草案，而是作为其规则部分的落地化细化设计。

---

## 2. 设计目标

当前阶段，规则系统的目标不是构建一个通用低代码平台，而是稳定解决以下问题：

1. 让用户可以定义一条可执行规则。
2. 让用户可以从某个属性出发，为该属性配置规则。
3. 让系统可以根据规则自动识别依赖属性。
4. 让物品编辑页可以基于规则补齐依赖输入并展示派生输出。
5. 让删除属性时可以通过规则判断影响范围。

因此当前设计必须满足：

- 简单属性仍然足够轻
- 复杂规则有统一模型
- 规则绑定能自然生成依赖关系
- 规则定义、规则详情、规则编辑、属性绑定、运行时执行使用同一套语言

---

## 3. 核心结论

当前阶段正式固定以下核心结论：

1. 规则最本质上是一个可执行表达式。
2. 用户定义规则时，真正定义的是：
   - 变量槽位
   - 来源类型
   - 绑定方式
   - 表达式
3. 规则绑定不是“属性简单绑定规则”，而是“从当前属性出发完成一条规则实例的组装”。
4. 属性之间的依赖关系不单独维护一套关系模型，而是从规则绑定中推导得到。
5. 第一阶段以表达式规则为主，不先做完整决策表 UI。
6. 第一阶段允许为槽位快捷新建属性，并默认回填当前规则绑定关系。

更抽象地说：

`规则 = 槽位化变量定义 + 槽位来源约束 + 绑定实例 + 表达式执行`

---

## 4. 顶层模型

当前阶段规则模型正式收敛为四个对象：

1. 规则定义
2. 槽位定义
3. 规则绑定实例
4. 规则输出

其中：

- 规则定义负责描述“这条规则长什么样”
- 槽位定义负责描述“这条规则有哪些输入输出变量”
- 规则绑定实例负责描述“某次使用这条规则时，每个槽位实际绑定到了什么”
- 规则输出负责描述“这条规则最终产生了什么结果，以及结果写到哪里”

---

## 5. 规则定义

## 5.1 规则定义是什么

规则定义回答的是：

- 这条规则叫什么
- 这条规则属于什么类型
- 这条规则有哪些输入槽位和输出槽位
- 这些槽位各自允许什么来源
- 这条规则的表达式是什么
- 这条规则在什么时机触发

规则定义本身不直接绑定某个具体属性。

也就是说：

- 规则定义是可复用的
- 规则定义不和某个具体业务字段写死
- 规则定义只是声明“我需要什么变量”

## 5.2 规则定义的核心字段

第一阶段建议规则定义严格收敛为以下字段：

1. 规则名
2. 规则类型
3. 槽位定义列表
4. 表达式定义
5. 输出策略
6. 触发方式
7. 描述

## 5.3 规则类型

规则类型用于表达规则的大类语义，不直接替代表达式本身。

第一阶段建议支持：

- 差值规则
- 平均值规则
- 周期规则
- 累计规则
- 条件规则
- 自定义表达式规则

说明：

- 规则类型主要用于管理页分类、模板归类、默认函数集提示与编辑页引导
- 真正的计算逻辑仍以表达式为准

## 5.4 表达式定义

第一阶段规则表达式正式采用“受限表达式语言”思路，不支持任意脚本执行。

表达式要满足以下边界：

- 可读
- 可校验
- 可序列化
- 可安全执行
- 可根据上下文重算

表达式第一阶段建议支持：

- 字面量
  - `1`
  - `"MONTH"`
  - `true`
  - `null`
- 变量引用
  - `price`
  - `startDate`
  - `currentDate`
- 算术运算
  - `+`
  - `-`
  - `*`
  - `/`
  - `%`
- 比较运算
  - `>`
  - `<`
  - `>=`
  - `<=`
  - `==`
  - `!=`
- 逻辑运算
  - `&&`
  - `||`
  - `!`
- 条件函数
  - `if(cond, a, b)`
- 空值处理
  - `coalesce(a, b, c)`
- 日期函数
  - `dateDiff(start, end, "DAY")`
  - `addPeriod(date, 1, "MONTH")`
- 周期函数
  - `cycleCount(start, end, chargeDay, cycleStep, cycleUnit)`
  - `cycleElapsed(start, current, cycleUnit)`
- 数值函数
  - `min`
  - `max`
  - `abs`
  - `round`

固定规则：

- 第一阶段不支持循环
- 第一阶段不支持任意副作用脚本
- 第一阶段不支持在表达式中直接写入属性
- 第一阶段不支持在表达式中使用 `+=` 这类命令式写法

规则表达式必须是声明式的。

例如：

- 推荐：
  - `remaining = totalPrice - deposit`
  - `totalPaid = cycleCount(startDate, endDate, chargeDay, cycleStep, cycleUnit) * price`
- 不推荐：
  - `if (...) { totalPaid += price }`

原因是：

- 声明式表达式天然支持重算
- 命令式累加会带来幂等性与重复执行问题

## 5.5 输出策略

规则不仅要知道“输出什么”，还要知道“输出怎么落地”。

第一阶段建议输出策略支持：

1. 只读结果
2. 属性写回
3. 系统变量写回

同时建议显式声明输出更新方式：

1. 覆盖型
2. 累计型

但第一阶段实际优先落地：

- 只读结果
- 覆盖型属性写回
- 系统变量写回

累计型先在模型中预留，不在第一阶段全面开放。

## 5.6 触发方式

规则需要声明什么时候重新计算。

第一阶段建议支持：

- 属性值变更时
- 表单打开时
- 保存物品时
- 相关系统变量变化时

说明：

- “周期规则”第一阶段先通过读取时间相关槽位和系统时间重算，不立即引入独立后台调度系统

---

## 6. 槽位定义

## 6.1 槽位定义是什么

槽位定义是规则模型的核心。

槽位定义回答的是：

- 这条规则里有哪些变量
- 每个变量是输入还是输出
- 每个变量是什么类型
- 每个变量允许从哪里取值
- 当前变量是否必须完成绑定

也就是说：

- 用户不是直接给属性随便绑规则
- 而是先让属性进入某条规则允许的槽位

## 6.2 槽位定义的核心字段

第一阶段建议槽位定义包含以下字段：

1. 槽位 key
2. 槽位名称
3. 槽位方向
4. 槽位值类型
5. 槽位来源类型
6. 是否必填
7. 是否允许快捷创建属性
8. 快捷创建属性预设
9. 描述

## 6.3 槽位方向

第一阶段固定为：

1. 输入槽位
2. 输出槽位

其中：

- 输入槽位用于表达式读取
- 输出槽位用于表达式产出

## 6.4 槽位值类型

第一阶段建议规则槽位值类型先与属性值类型体系尽量对齐，并在规则层补充少量系统类型。

建议支持：

- 文本
- 数值
- 日期
- 布尔
- 选择
- 周期单位
- 系统日期时间

说明：

- 对于属性层已有类型，优先复用已有认知
- 对于规则层特有配置，例如 `MONTH`、`WEEK`、`QUARTER`，可视作“周期单位”枚举值

## 6.5 槽位来源类型

当前阶段建议固定为以下几类：

1. 属性输入
2. 配置输入
3. 系统输入
4. 属性输出
5. 只读输出
6. 系统输出

统一说明如下：

- `属性输入`
  - 需要绑定到某个具体属性
- `配置输入`
  - 不来自属性，由用户在绑定规则时直接填写
- `系统输入`
  - 来自系统级变量
- `属性输出`
  - 输出结果写回某个属性
- `只读输出`
  - 仅作为运行结果显示
- `系统输出`
  - 输出结果写回系统级变量

## 6.6 快捷创建属性能力

这是第一阶段必须纳入正式设计的便捷能力。

当某个槽位允许快捷创建属性时，用户在补齐规则绑定时，可以：

- 直接输入一个名称
- 系统按照该槽位的值类型与默认预设快速创建属性
- 创建成功后自动把该属性绑定到当前槽位
- 同时把该属性与当前规则实例关联起来

例如：

- 槽位：`chargeDay`
- 要求：日期类型、属性输入
- 当前没有现成属性
- 用户直接输入：`订阅日`

系统行为：

1. 创建一个名为 `订阅日` 的日期属性
2. 该属性默认值来源设为 `输入`
3. 该属性默认交互方式设为日期输入控件
4. 自动绑定到当前规则实例的 `chargeDay` 槽位

固定规则：

- 仅 `属性输入` 与 `属性输出` 槽位允许开启快捷创建属性
- `配置输入` 与 `系统输入` 不允许快捷创建属性
- 快捷创建属性时必须继承槽位类型约束，不允许用户创建不兼容类型

## 7. 规则绑定实例

## 7.1 规则绑定实例是什么

规则绑定实例回答的是：

- 某次实际使用这条规则时，每个槽位绑定到了什么

这里需要特别强调：

- 绑定实例不等于规则定义
- 规则定义是母版
- 绑定实例是“这条规则在某个属性配置中的一次具体落地”

## 7.2 为什么绑定实例是核心对象

因为用户真正使用规则时，发生的是：

1. 从当前属性出发，选择一条规则
2. 把当前属性绑定到该规则允许的某个输入槽位
3. 再补齐该规则剩余槽位
4. 最终形成一条完整的可执行规则实例

所以系统真正要持久化和分析的，是“规则实例绑定图”，而不是单纯“属性拥有规则名”。

## 7.3 绑定实例的核心字段

第一阶段建议规则绑定实例至少包含：

1. 绑定实例 id
2. 规则定义 id
3. 当前入口属性 id
4. 属性槽位绑定表
5. 配置槽位绑定表
6. 系统槽位绑定表
7. 输出槽位绑定表
8. 创建方式
9. 是否完整
10. 描述

## 7.4 绑定实例中的几类绑定

### 7.4.1 属性槽位绑定

表示：

- 某个输入槽位由哪个属性提供值

例如：

- `price -> QQ会员价格`
- `chargeDay -> 订阅日`

### 7.4.2 配置槽位绑定

表示：

- 某个输入槽位不是来自属性，而是直接保存配置值

例如：

- `startDate -> 2026-01-01`
- `cycleStep -> 1`
- `cycleUnit -> MONTH`

### 7.4.3 系统槽位绑定

表示：

- 某个输入槽位来自系统级变量

例如：

- `currentDate -> CURRENT_DATE`

### 7.4.4 输出槽位绑定

表示：

- 某个输出槽位最后写到哪里

例如：

- `totalPaid -> 累计总价`
- `nextChargeDate -> NEXT_REMINDER_AT`

## 7.5 绑定完整性的判定

一条绑定实例只有在以下条件全部满足后，才算完整：

1. 所有必填输入槽位都已绑定
2. 所有必填输出槽位都已绑定
3. 所有绑定都通过类型检查
4. 表达式中的变量引用都能在绑定上下文中找到

未完成绑定的规则实例：

- 允许以草稿状态存在
- 不进入运行时执行
- 不计入物品编辑页自动补齐逻辑

## 8. 从属性出发的规则绑定流程

## 8.1 入口场景

第一阶段，最主要的规则配置入口是：

- 用户在属性管理页中，从某个属性出发添加规则

例如：

- 当前属性：`QQ会员价格`
- 用户点击：添加规则

## 8.2 槽位候选过滤

当用户从某个属性出发添加规则时，系统不应展示所有槽位，而应只展示兼容当前属性的槽位。

槽位候选过滤规则如下：

1. 当前属性只能进入输入槽位，不能进入输入方向不兼容的输出槽位。
2. 当前属性的值类型必须与槽位值类型兼容。
3. 当前属性的值来源与交互方式如不满足槽位约束，不允许绑定。
4. 当前属性不能重复绑定到同一规则实例中多个语义冲突的槽位。

例如：

- 当前属性是数值属性 `QQ会员价格`
- 系统只显示：
  - `price`
  - `subscriptionPrice`
  - `amount`
- 不显示：
  - `chargeDay`
  - `isExpired`
  - `totalPaid`

## 8.3 槽位补齐向导

一旦用户把当前属性绑定到某个槽位，系统就进入“补齐剩余槽位”的向导流程。

该向导应按槽位类型分别给出操作方式：

- 对于 `属性输入` 槽位：
  - 选择已有兼容属性
  - 快捷新建兼容属性
- 对于 `配置输入` 槽位：
  - 直接填写配置值
- 对于 `系统输入` 槽位：
  - 选择系统变量或使用默认系统槽位
- 对于 `属性输出` 槽位：
  - 选择已有兼容属性
  - 快捷新建兼容输出属性
- 对于 `只读输出` 槽位：
  - 无需额外配置落点
- 对于 `系统输出` 槽位：
  - 选择系统变量目标

## 8.4 快捷新建属性的正式流程

当用户在补齐剩余属性槽位时，可直接输入名称快捷创建依赖属性。

推荐流程如下：

1. 用户在槽位候选中没有找到需要的属性。
2. 用户直接输入名称，例如 `订阅日`。
3. 系统校验该名称是否可用。
4. 系统按照槽位默认预设创建属性定义。
5. 系统自动将新属性绑定到当前槽位。
6. 当前规则实例继续留在补齐页，不中断上下文。

这个能力的目标是：

- 避免用户跳出规则配置流程
- 避免用户先去属性管理页手动建属性再返回
- 让依赖属性的创建与规则绑定同时完成

## 9. 依赖关系如何从绑定中推导

## 9.1 不单独建立关系模型

当前阶段仍然不单独建立第三套“关系模型”。

原因是：

- 规则绑定本身已经提供了足够稳定的依赖语义
- 再额外维护一套关系模型会增加系统复杂度与用户心智负担

## 9.2 依赖推导规则

从规则绑定实例推导依赖关系时，建议固定以下规则：

1. 当前规则实例中所有 `属性输入` 槽位绑定的属性，互为输入依赖集合。
2. `属性输出` 槽位绑定的属性，视为该输入依赖集合共同影响的派生属性。
3. `配置输入` 槽位与 `系统输入` 槽位不产生新的属性依赖节点，但会成为规则执行上下文的一部分。
4. `只读输出` 不新增属性节点，但会形成派生结果。

## 9.3 从当前属性出发的依赖理解

当用户从当前属性出发配置规则时：

- 当前属性先占据某个槽位
- 规则中的其他 `属性输入` 槽位，自然变成该属性依赖的其他属性
- 规则中的 `属性输出` 槽位，自然变成该属性会影响的派生属性

这正是物品编辑页自动补齐与属性删除影响分析的统一来源。

## 10. 与物品编辑页的联动

## 10.1 基本原则

物品编辑页不直接理解“抽象规则语言”，只消费规则绑定推导出来的结果。

推荐流程如下：

1. 用户为物品添加某个属性
2. 系统读取该属性关联的规则绑定实例
3. 收集该规则实例中所有必填 `属性输入` 槽位
4. 若尚未出现在当前填写清单，则自动补齐
5. 运行表达式，生成输出结果
6. 只读输出显示为派生结果
7. 属性输出与系统输出按对应策略写回

## 10.2 自动补齐边界

第一阶段自动补齐只针对：

- 必填的 `属性输入` 槽位

不自动补齐：

- 可选属性输入
- 配置输入
- 系统输入
- 规则输出

## 10.3 表单中的输出边界

第一阶段表单中优先支持：

- 只读输出展示
- 必要的属性写回

推荐规则：

- 只读输出显示为“规则结果卡片”
- 属性写回输出优先显示为只读派生属性
- 系统输出不直接暴露为普通表单字段

## 11. 删除属性的影响分析

## 11.1 为什么现在可以做精确分析

因为属性删除影响现在不再只依赖“模糊规则名”，而是可以直接读取绑定实例中该属性扮演的槽位角色。

## 11.2 删除属性时需要判断的内容

删除某个属性时，系统需要检查：

1. 它是否被用作某条规则实例的输入槽位
2. 它是否被用作某条规则实例的输出槽位
3. 删除后会导致哪些规则实例不完整
4. 删除后会影响哪些派生属性或只读输出

## 11.3 推荐提示语义

删除影响提示不应再只写：

- “该属性绑定了规则，请检查”

而应明确说明：

- 该属性被哪些规则实例使用
- 它在这些规则中是输入、输出还是依赖属性
- 删除后将影响哪些属性结果

例如：

- `订阅日` 当前被规则 `周期扣费` 用作输入槽位 `chargeDay`
- 影响入口属性：`QQ会员价格`
- 影响输出属性：`累计总价`
- 删除后该规则实例将失效

## 12. 周期扣费规则示例

## 12.1 规则定义示例

规则名：

- `周期扣费`

规则类型：

- `周期规则`

槽位定义：

1. `price`
   - 输入槽位
   - 数值
   - 属性输入
   - 必填
2. `chargeDay`
   - 输入槽位
   - 日期
   - 属性输入
   - 必填
   - 允许快捷创建属性
3. `startDate`
   - 输入槽位
   - 日期
   - 配置输入
   - 必填
4. `endDate`
   - 输入槽位
   - 日期
   - 配置输入
   - 可选
5. `cycleStep`
   - 输入槽位
   - 数值
   - 配置输入
   - 必填
6. `cycleUnit`
   - 输入槽位
   - 周期单位
   - 配置输入
   - 必填
7. `currentDate`
   - 输入槽位
   - 系统日期时间
   - 系统输入
   - 必填
8. `totalPaid`
   - 输出槽位
   - 数值
   - 属性输出
   - 必填
   - 允许快捷创建属性

表达式：

- `cycleCount(startDate, coalesce(endDate, currentDate), chargeDay, cycleStep, cycleUnit) * price`

输出策略：

- 属性写回
- 覆盖型

## 12.2 从属性出发的绑定示例

当前属性：

- `QQ会员价格`

用户把它绑定到：

- `price`

系统继续引导补齐：

- `chargeDay`
  - 用户输入：`订阅日`
  - 系统快捷创建日期属性并自动绑定
- `totalPaid`
  - 用户输入：`累计总价`
  - 系统快捷创建数值属性并自动绑定
- `startDate`
  - 用户选择：`2026-01-01`
- `cycleStep`
  - 用户选择：`1`
- `cycleUnit`
  - 用户选择：`MONTH`
- `currentDate`
  - 系统默认注入：`CURRENT_DATE`

由此形成：

- 入口属性：`QQ会员价格`
- 依赖属性：`订阅日`
- 配置输入：`startDate`、`cycleStep`、`cycleUnit`
- 系统输入：`currentDate`
- 输出属性：`累计总价`

这就是一条完整的规则绑定实例。

## 13. 第一阶段固定边界

## 13.1 当前正式支持

- 表达式型规则定义
- 槽位化输入输出定义
- 属性输入、配置输入、系统输入
- 只读输出、属性输出、系统输出
- 从属性出发的规则绑定流程
- 槽位候选过滤
- 槽位补齐向导
- 快捷新建依赖属性
- 基于绑定实例的依赖推导
- 物品表单自动补齐必填依赖
- 删除属性影响分析

## 13.2 当前不优先支持

- 完整决策表可视化编辑器
- 任意脚本执行
- 通用低代码流程编排
- 多阶段异步规则执行管线
- 独立关系模型治理平台

## 15. 当前设计稿的最终结论

当前可以正式固定以下结论：

1. 规则最本质上是一个可执行表达式。
2. 规则定义必须围绕“槽位”建模，而不是直接写死具体属性名。
3. 槽位必须显式声明方向、值类型、来源类型和是否必填。
4. 规则绑定的真正对象是“绑定实例”，不是简单的规则名列表。
5. 用户从属性出发配置规则时，系统要先做槽位候选过滤，再做剩余槽位补齐。
6. 剩余属性槽位的配置必须支持快捷新建属性，并自动回填当前规则绑定。
7. 属性之间的依赖关系，不单独维护一套关系模型，而是从规则绑定实例中推导。
8. 物品编辑页的依赖补齐与属性删除影响分析，统一建立在同一套规则绑定语义之上。
9. 第一阶段以表达式规则为主，不先做完整决策表 UI。
10. 第一阶段的规则系统目标是“让规则可定义、可绑定、可执行、可分析”，而不是做通用低代码平台。
