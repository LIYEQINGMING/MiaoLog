# 规则定义编辑页设计文档 v1

## 1. 文档定位

本文档用于在当前已落地的 V1 规则模型基础上，正式收口“规则新建页改为 AST 编辑器”后的边界与最小可落地版本。

本文档重点回答：

- AST 编辑器到底负责什么
- AST 编辑器必须复用哪些现有模型
- 哪些能力属于变量管理，不属于 AST 本体
- 哪些能力本轮必须做，哪些明确不做

本文档主要对应：

- `AttributeManagementRouteState.RuleEditor`
- `RuleEditorPage`
- `RuleEditorDraftUiModel`
- `AttributeManagementViewModel.saveRuleDraft()`

---

## 2. 结论先行

当前可以直接固定的结论如下：

1. 规则编辑页从“槽位表单 + 表达式文本框”升级为“基本信息 + 变量管理 + AST 公式编辑 + 保存”。
2. AST 只负责承载“表达式结构”，不替代 `RuleDefinition`、`RuleSlotDefinition`、`RuleBindingInstance`。
3. 变量仍然以 `slot` 为正式模型落库，AST 中只引用变量，不重复定义变量。
4. 常量不作为槽位管理，常量直接进入 AST 字面量节点。
5. 系统变量继续通过 `SYSTEM_INPUT` 槽位建模，而不是绕开槽位体系单独塞进 AST。
6. 输出槽位继续留在规则元数据层，不在 MVP 中做“赋值语句节点”。
7. `triggerModes` 继续保留在底层模型与仓储中，但从规则新建页用户交互中移除，当前统一按内部默认值处理。
8. MVP 先做 AST 结构编辑器，不做自由拖拽画布、不做缩放 Canvas、不做撤销重做、不做通用文本双向转换。

---

## 3. 页面定位

规则定义编辑页负责“创建或修改规则母版”，不直接负责规则绑定实例。

它负责：

- 定义规则名称、说明、规则类型
- 定义输入变量与输出变量
- 用 AST 方式编辑单条受限表达式
- 定义输出策略
- 做保存前结构校验

它不负责：

- 把当前属性绑定到某个槽位
- 补齐某条规则实例的配置值
- 查看某个物品上的实时运行结果
- 提供任意脚本编写能力
- 充当通用低代码画布

固定原则：

- `编辑页负责定义规则母版`
- `绑定页负责组装规则实例`
- `运行时负责求值与写回`

---

## 4. 与当前实现的关系

本轮不是重做规则主模型，而是重做规则编辑方式。

### 4.1 继续复用的正式模型

AST 编辑器必须继续复用以下结构：

- `RuleDefinition`
- `RuleSlotDefinition`
- `RuleExpressionDefinition`
- `RuleOutputStrategyDefinition`

保存后的正式结果仍然是：

```text
RuleDefinition
- 基本信息
- slots
- expressionDefinition
- outputStrategies
- description
- templateId
```

### 4.2 当前不改的运行时边界

以下链路本轮不推翻：

- 物品编辑页按绑定实例自动补齐必填属性输入
- `ATTRIBUTE_INPUT` 固定必填
- 规则运行时按槽位上下文求值
- 表达式最终仍编译为受限表达式字符串执行

### 4.3 本轮主要变化点

变化发生在“编辑器层”：

- 变量不再主要靠大段槽位表单堆叠
- 表达式不再以自由文本输入为主
- 用户通过可视化 AST 结构来组装公式

---

## 5. AST 编辑器职责边界

### 5.1 AST 负责什么

AST 只负责表达：

- 字面量
- 变量引用
- 运算符组合
- 函数调用
- 条件结构

也就是说，AST 负责的是：

- `规则怎么算`

### 5.2 AST 不负责什么

AST 不负责表达：

- 变量从哪里来
- 变量能不能快捷创建属性
- 当前变量是输入还是输出
- 输出要写回哪个目标
- 规则什么时候触发
- 某个变量绑定到了哪个具体属性

这些继续由槽位与输出策略承载。

也就是说，以下信息不进入 AST：

- `slot.sourceType`
- `slot.direction`
- `slot.isRequired`
- `slot.allowQuickCreateAttribute`
- `outputStrategy.targetType`
- `triggerModes`

### 5.3 为什么这样切边界

这样设计的原因是：

- 当前运行时、绑定页、依赖分析都已经建立在槽位模型上
- 如果把变量来源、绑定目标、执行时机也塞进 AST，会把编辑器复杂度放大得过快
- 当前最需要升级的是“公式表达体验”，不是再引入一套新主模型

---

## 6. 变量模型边界

规则编辑页中的“变量”不是新的持久化主对象，本质上是对 `slots` 的用户友好呈现。

### 6.1 变量分类

MVP 中变量固定分为四类：

1. 属性输入变量
2. 配置输入变量
3. 系统输入变量
4. 输出变量

映射关系如下：

- 属性输入变量 -> `INPUT + ATTRIBUTE_INPUT`
- 配置输入变量 -> `INPUT + CONFIG_INPUT`
- 系统输入变量 -> `INPUT + SYSTEM_INPUT`
- 输出变量 -> `OUTPUT + ATTRIBUTE_OUTPUT / READONLY_OUTPUT / SYSTEM_OUTPUT`

### 6.2 常量的处理方式

常量不进入变量列表对应的正式槽位定义。

固定策略：

- 临时常量直接作为 AST 字面量节点
- 如果用户希望某个值在绑定规则时可配置，则它不应是常量，而应建成 `CONFIG_INPUT`

这条规则可以明显减少“变量很多但大多只是常量”的噪音。

### 6.3 输出变量的 AST 边界

输出变量在 MVP 中用于声明“结果写到哪里”，不作为表达式中的赋值节点参与编辑。

固定策略：

- AST 只编辑一个返回值表达式
- 输出槽位单独配置
- 保存时由 `outputStrategies` 决定结果写回方式

这意味着 MVP 不支持：

- `totalPaid += price`
- `set(totalPaid, xxx)`
- 多条语句顺序执行

需要表达累计、条件、周期等语义时，统一改写为声明式表达式。

---

## 7. AST 数据模型边界

### 7.1 根节点

MVP 固定为单根表达式：

```text
ExpressionRoot
└─ ExprNode
```

这与当前 `RuleExpressionDefinition.expression` 的单表达式边界保持一致。

### 7.2 MVP 节点类型

MVP 必须支持的节点类型：

1. `Literal`
2. `VariableRef`
3. `UnaryOp`
4. `BinaryOp`
5. `FunctionCall`
6. `Conditional`

建议的最小结构：

```kotlin
sealed interface RuleAstNode {
    val id: String
}

data class LiteralNode(...)
data class VariableRefNode(...)
data class UnaryOpNode(...)
data class BinaryOpNode(...)
data class FunctionCallNode(...)
data class ConditionalNode(...)
```

### 7.3 MVP 运算能力

MVP 建议直接覆盖当前规则设计最常见场景：

- 算术运算：`+` `-` `*` `/` `%`
- 比较运算：`>` `<` `>=` `<=` `==` `!=`
- 逻辑运算：`&&` `||` `!`
- 条件函数：`if(cond, a, b)`
- 空值函数：`coalesce(...)`
- 数值函数：`min` `max` `abs` `round`
- 日期函数：`dateDiff` `addPeriod`
- 周期函数：`cycleCount` `cycleElapsed`

### 7.4 MVP 明确不支持的节点

本轮明确不支持：

- 赋值节点
- 多语句块
- 循环节点
- 自定义函数定义
- Lambda
- 副作用命令
- 任意脚本节点

## 8. UI / UX 方案

### 8.1 页面主流程

规则新建流程固定为：

1. 填写名称与说明
2. 添加变量
3. 在 AST 编辑器中组装公式
4. 保存规则

顶部不再需要旧的规则预览卡片。

### 8.2 页面推荐结构

```text
规则定义编辑
- 基本信息
- 变量区
  - 添加变量按钮
  - 已添加变量抽屉 / 列表
- 公式编辑区
  - AST 结构编辑器
  - 当前公式文本预览
  - 校验反馈
- 输出区
  - 输出变量概览
  - 输出策略
- 保存区
```

### 8.2.1 页面信息架构建议

为了兼顾表单录入、变量管理和 AST 编辑，页面建议采用“顶部操作栏 + 主内容双栏”的稳定结构：

```text
顶部操作栏
- 返回
- 页面标题
- 保存按钮

主内容区
- 左栏
  - 基本信息
  - 变量区
  - 输出区
- 右栏
  - AST 公式编辑区
  - 节点属性区
  - 文本预览与校验反馈
```

推荐原因：

- 左栏承载规则元数据与变量管理，信息密度稳定
- 右栏聚焦“当前正在编辑的表达式”，避免用户频繁跳上下文
- 保存按钮固定在顶部，减少长页滚动后找不到主要动作的问题

### 8.2.2 模块展开策略

为了避免页面初看过重，建议固定以下展开策略：

- `基本信息` 默认展开
- `变量区` 默认展开
- `输出区` 默认折叠，但存在输出校验错误时自动展开
- `节点属性区` 在未选中节点时显示空态提示
- `文本预览与校验反馈` 常驻底部或右侧，不允许完全隐藏

这样可以保证：

- 新用户先完成“命名 + 变量准备”
- 公式编辑时始终看得到当前表达式预览和错误信息
- 输出配置不会被遗忘，但也不会在首屏抢占过多注意力

### 8.3 添加变量弹窗

“添加变量”弹窗负责新增或编辑一个槽位。

MVP 中弹窗至少支持：

- 变量名称
- 变量 key
- 变量类型
- 变量分类
- 系统变量选择
- 是否允许快捷创建属性
- 输出目标类型
- 描述

交互约束：

- 属性输入固定必填，不再暴露“可选输入”
- 非法方向/来源组合不允许出现
- 输出变量的目标类型只展示合法选项

### 8.3.1 变量弹窗交互细节

变量弹窗建议采用“基础字段 + 动态字段”的表单策略：

- 基础字段始终显示：名称、key、值类型、分类、描述
- 当分类是 `系统输入变量` 时，显示系统变量选择器
- 当分类是 `输出变量` 时，显示输出目标类型与输出策略提示
- 当分类是 `属性输入变量` 或 `属性输出变量` 时，显示“是否允许快捷创建属性”

建议补充以下默认行为：

- 名称输入后自动生成 `key`，但允许用户手改
- `key` 一旦被 AST 引用，编辑时需要做二次确认
- 编辑已有变量时，若修改会导致现有 AST 节点失效，需明确提示影响范围

### 8.4 已添加变量区

变量区建议采用抽屉或折叠列表，而不是长表单平铺。

每个变量卡片至少展示：

- 名称
- key
- 类型
- 来源
- 输入/输出标记
- 是否允许快捷创建属性

从这里支持：

- 编辑变量
- 删除变量
- 在公式中插入变量引用

### 8.4.1 变量列表排序建议

变量列表建议固定按以下顺序分组展示：

1. 属性输入变量
2. 配置输入变量
3. 系统输入变量
4. 输出变量

每组内再按创建顺序或名称排序。

这样处理的好处是：

- 用户更容易理解“哪些变量是外部依赖、哪些只是配置、哪些是结果”
- 与绑定页的槽位补齐顺序保持一致
- 后续做依赖分析和错误提示时更容易定位

### 8.4.2 删除变量的保护规则

删除变量时不应直接删除成功，建议区分两种情况：

- 变量未被 AST 引用：允许直接删除
- 变量已被 AST 引用：弹出确认框，并列出受影响的节点或表达式片段

如果删除的是唯一输出变量，还应额外提示：

- 删除后规则将无法形成完整输出，保存会被阻止

### 8.5 公式编辑区

MVP 推荐采用“树形结构编辑器”而不是“自由画布编辑器”。

固定结论：

- 核心数据模型是 AST
- 但第一版 UI 不做 Compose Canvas 自由拖拽
- 第一版采用结构化节点卡片、分层嵌套、按钮式插入

这样可以明显降低实现成本，同时仍然符合“基于 AST 编辑”的方向。

公式编辑区至少包含：

- 根表达式节点
- 运算符 / 函数插入入口
- 变量插入入口
- 常量插入入口
- 当前选中节点的属性编辑区
- 只读表达式文本预览

### 8.5.1 AST 编辑交互建议

为了让第一版树形编辑器可用而不过重，建议固定以下交互：

- 所有节点都支持“替换当前节点类型”
- 所有可接子节点的位置都显示明确的“插入”入口
- 变量节点通过选择已有变量创建，不支持手输不存在的变量 key
- 常量节点直接编辑字面量值，但应受值类型限制
- 函数节点先选函数，再按函数签名补参数槽位
- 条件节点固定显示 `条件 / 为真时 / 为假时` 三段结构

推荐原因：

- 用户始终在“合法 AST”范围内编辑
- 不需要处理太多自由文本纠错
- 可以天然减少运行时不认识的表达式组合

### 8.5.2 节点空态与引导

公式编辑区应有明确的空态，而不是显示空白区域。

推荐空态动作：

- 插入变量
- 插入常量
- 插入二元运算
- 插入函数
- 插入条件表达式

当用户尚未添加任何输入变量时，优先提示：

- 请先添加变量，再开始组装公式

### 8.5.3 节点属性面板建议

节点属性面板不应做成通用大表单，而应按节点类型展示必要字段：

- `Literal`：值、值类型
- `VariableRef`：变量选择、显示名
- `UnaryOp`：运算符、子节点
- `BinaryOp`：运算符、左节点、右节点
- `FunctionCall`：函数名、参数列表、函数说明
- `Conditional`：条件节点、真分支、假分支

同时建议在属性面板中同步展示：

- 当前节点编译后的表达式片段
- 当前节点的类型或预期返回类型
- 当前节点的局部校验结果

### 8.6 文本预览策略

MVP 先采用：

- `AST -> 表达式字符串` 单向生成

本轮不要求完整实现：

- 自由文本输入 -> AST 的双向实时转换

### 8.6.1 校验反馈分层

规则定义页不应只在点击保存时才发现问题，建议把校验反馈分为三层：

1. 阻止保存的错误
2. 允许保存但需要提醒的警告
3. 纯提示类信息

建议的错误来源包括：

- 基本信息缺失
- 变量定义不合法
- AST 结构不完整
- AST 引用了不存在的变量
- 输出配置不合法

建议的警告来源包括：

- 已定义变量但未被引用
- 存在多个输出变量但当前表达式只有单结果
- 表达式复杂度过高

建议的提示来源包括：

- 可将常量改为配置输入以提升复用性
- 某些函数更适合当前规则类型

### 8.6.2 保存按钮可用条件

保存按钮建议不是简单的“永远可点”，而应基于阻止保存的错误状态决定：

- 无阻止保存错误时可点击保存
- 有阻止保存错误时按钮置灰，并在按钮附近显示摘要说明

如果产品侧仍希望允许点击保存再统一提示，也应在点击后把页面自动滚动到首个错误模块。

### 8.6.3 表达式预览与调试边界

第一版可以不做真实运行时调试，但建议至少提供两类轻量反馈：

- 编译后的表达式字符串预览
- AST 分析摘要

AST 分析摘要推荐包含：

- 引用变量列表
- 节点数量
- 树深度
- 复杂度评分

这些信息不直接暴露给普通用户也可以先用于开发调试和后续静态分析。

### 8.6.4 离开页面与未保存提示

规则定义页属于高编辑成本页面，建议明确未保存离开策略：

- 草稿有变更且未保存时，返回操作弹出确认提示
- 提供 `继续编辑` / `放弃修改` 两个主选项
- 如果后续要支持自动草稿保存，也应明确区分“本地编辑态”与“正式保存成功”

## 9. 保存映射方案

### 9.1 变量到正式模型的映射

变量编辑器保存后，仍然回写为 `RuleSlotDefinition`：

- 变量弹窗草稿 -> `RuleSlotDraftUiModel`
- 保存规则时 -> `RuleSlotDefinition`

### 9.2 AST 到正式模型的映射

AST 保存时统一编译为：

- `expressionDefinition.expression`
- `expressionDefinition.referencedSlotKeys`

其中：

- `expression` 为受限表达式字符串
- `referencedSlotKeys` 从 AST 中的 `VariableRef` 节点提取

### 9.3 输出策略映射

输出变量继续转换为：

- `RuleOutputStrategyDefinition`

输出策略不从 AST 推导，而是从输出变量配置直接生成。

### 9.4 triggerModes 的处理

当前固定策略：

- `triggerModes` 从规则编辑页 UI 中移除
- `ViewModel.saveRuleDraft()` 继续在保存时兜底默认 `ON_VALUE_CHANGED`
- 模板与系统规则仍可在底层保留该字段

也就是说：

- `triggerModes` 暂时是内部实现字段，不是用户显式配置字段

## 10. 编辑态状态建议

当前 `RuleEditorDraftUiModel` 仍是旧结构，但 AST 方案落地后应演进为“两层状态”：

1. 规则正式草稿
2. 编辑器临时状态

推荐方向如下：

```kotlin
data class RuleEditorDraftUiModel(
    val id: String? = null,
    val name: String = "",
    val description: String = "",
    val templateId: String? = null,
    val templateName: String? = null,
    val computationType: RuleComputationType = RuleComputationType.CUSTOM,
    val slots: List<RuleSlotDraftUiModel> = emptyList(),
    val expressionAst: RuleAstNode? = null,
    val expressionPreview: String = "",
    val selectedNodeId: String? = null,
    val systemVariableOptions: List<SystemVariableOptionUiModel> = emptyList(),
    val title: String = "新建规则",
    val saveButtonText: String = "保存规则",
    val isEditMode: Boolean = false,
)
```

说明：

- `slots` 继续作为正式变量定义来源
- `expressionAst` 是编辑器主状态
- `expressionPreview` 是编译后的只读预览
- `selectedNodeId` 用于节点属性面板

`triggerModes` 可以先保留在草稿模型中做过渡，但不再在页面上暴露交互。

### 10.1 编辑已有规则时的页面策略

规则定义页不仅服务于新建规则，也要兼容编辑已有规则。

编辑模式下建议补充以下行为：

- 页面标题切为 `编辑规则`
- 优先回显已有 `slots`、输出策略和 AST 草稿
- 若规则来源于旧文本表达式且尚未迁移为 AST，显示迁移提示而不是直接进入空白编辑器

对于无法直接恢复为 AST 的旧规则，建议提供：

- 只读表达式查看
- 当前不可可视化编辑的原因说明
- 引导用户基于现有规则新建一份 AST 版本，或走定向迁移流程

---

## 11. 兼容与迁移策略

当前阶段仍在开发期，因此本轮不建议为了旧文本表达式做过重兼容。

固定策略：

1. MVP 必做 `AST -> 表达式字符串` 编译。
2. MVP 不强求完整的“任意旧表达式字符串 -> AST”解析器。
3. 对于系统内置模板或开发期样例，优先通过模板重建或定向迁移到 AST 草稿。
4. 对于超出支持函数集的旧表达式，允许提示“当前规则需迁移后再进入可视化编辑”。

这样可以避免一开始就为了兼容自由文本而把 AST 编辑器做得过重。

---

## 12. MVP 必做项

本轮最小可落地版本固定为：

1. 去掉规则编辑页中的触发方式用户配置。
2. 去掉旧的“槽位长表单 + 自由表达式大文本框”主交互。
3. 增加“添加变量”弹窗与变量列表。
4. 增加 AST 树形公式编辑区。
5. 支持变量引用、常量、运算符、函数、条件节点。
6. 支持 AST 编译为受限表达式字符串。
7. 保存时继续落到 `RuleDefinition.slots + expressionDefinition + outputStrategies`。
8. 做基础校验：
   - 规则名不能为空
   - 至少 1 个输入变量
   - 至少 1 个输出变量
   - 变量 key 不重复
   - AST 非空
   - AST 中引用的变量都存在
   - 输出变量配置合法

---

## 13. MVP 暂不做项

本轮明确不做：

- 自由拖拽节点画布
- 缩放 / 平移 / 连线式 Canvas
- 撤销 / 重做 Command 系统
- 通用文本与可视化双向实时同步
- 多语句规则
- 赋值语法
- AST 调试器
- 自动类型推导全覆盖
- 多返回值表达式
- 基于 AST 的规则模板市场级能力

其中最重要的一条是：

- `先做 AST 结构编辑器，不做低代码画布平台`

---

## 14. 关于多输出的当前收口

当前底层模型允许存在多个输出槽位，但 AST 仍然是单表达式。

因此 MVP 固定边界为：

- 页面层仍允许定义多个输出槽位
- 但 AST 只表达一个结果值
- 第一版优先保证“单结果 -> 单主输出槽位”完整跑通

如果后续要正式开放多输出，可考虑再扩展：

- 单表达式返回复合结果
- 输出槽位映射到结果字段
- 或引入受限赋值节点

这不是本轮 MVP 的目标。

---

## 15. 最终结论

当前可以正式固定的 AST 编辑器方案如下：

1. AST 编辑器只重构规则编辑体验，不重构规则主模型。
2. 变量继续以 `slots` 为正式存储模型，AST 只引用变量。
3. 常量进入 AST 字面量节点，系统变量继续通过系统输入槽位建模。
4. 输出仍由输出槽位与输出策略承载，不在 MVP 中做赋值语句。
5. `triggerModes` 从用户页面移除，保留为内部默认字段。
6. MVP 采用树形 AST 编辑器，而不是自由拖拽画布。
7. MVP 只要求 `AST -> 表达式字符串` 单向编译，不要求重兼容的双向转换。
8. 保存结果继续稳定回写到当前 `RuleDefinition` 结构，确保与已落地的绑定页、运行时、依赖补齐逻辑保持一致。
